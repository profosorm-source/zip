# استراتژی پوشش کامل تست — اکشن‌محور / رانتایم‌محور / مرورگرمحور / منطق‌محور / E2E

این سند بر پایهٔ **اندازه‌گیری واقعی روی کد**، نه تخمین، نوشته شده.

## ۰) خلاصهٔ مدیریتی

پروژه از نظر «تعداد تست» غنی است (۲۵۸ فایل PHPUnit، ۴۸ اسکریپت Python،
۳۴ اسکریپت مرورگری) اما دو **شکاف ساختاری** دارد که تا رفع نشوند، افزودن
تست بیشتر ارزش واقعی اضافه نمی‌کند:

1. **۲۷ از ۳۴ تست مرورگری از نظر فنی نمی‌توانند شکست بخورند.**
2. **روت‌های پارامتردار عملاً بدون پوشش‌اند: ۱۲٪ در برابر ۸۴٪ روت‌های ثابت.**

اولویت درست: **اول کف را درست کن، بعد سقف را بالا ببر.**

## ۲) شکاف بحرانی: تست‌های مرورگری که نمی‌توانند شکست بخورند

۲۷ از ۳۴ فایل `browser_*.js` این ساختار را دارند:

```js
try {
  await page.goto(...);
  await page.fill('input[name="email"]', 'admin@chortke.ir');
  await page.click('button[type="submit"]');
  console.log('✓ ورود با موفقیت انجام شد.');   // ← بدون هیچ تأییدی!
} catch (e) {
  console.log('✗ خطای تست مرورگر: ' + e.message);  // خطا بلعیده می‌شود
} finally {
  console.log('✓ پایان تست مرورگری');            // همیشه چاپ می‌شود
}
```

**اثبات عملی** (اجرا شد): سناریوی یکسان با یک خطای واقعی →
`✗` چاپ شد، `✓ پایان تست` هم چاپ شد، و **`EXIT CODE = 0`**.

چرا مهلک است: `tests/run_all.py` در تابع `run_browser_test` (خط ۲۹۲) فقط
`return result.returncode == 0` را می‌خواند. خطوط `✗` را قرمز **چاپ** می‌کند
ولی در نتیجه **لحاظ نمی‌کند**. یعنی «لایه ۷ سبز» یک توهم است.

آمار مؤید: در ۳۴ فایل، ۱۸۵ بار `✓` چاپ می‌شود، ۱۹۰ بار `goto`، ۱۸۲ اکشن
(`click/fill/type`) — ولی **صفر** `assert`/`expect`، و تنها ۴۶ فراخوانی `check(`
که همه در همان ۷ فایل سالم‌اند.

**۷ فایل سالم** (دارای `process.exit(1)`) الگوی مرجع‌اند:
`browser_0_to_100_full_platform_e2e`, `browser_advanced_action_driven`,
`browser_earning_and_user_mgmt_e2e`, `browser_grand_lifecycle_saga`,
`browser_logic_auth_profile`, `browser_logic_financial_treasury`,
`browser_logic_security_fraud`.

## ۳) شکاف دوم: ادعاهای چندحالته

در نسخهٔ patch‌شده **۱۴۸** ادعای `in (200, 302)` باقی است.
`(200,302,404)` تقریباً حذف شده — فقط **۱** مورد مانده:
`tests/scenario_admin_governance.py:45`.

`in (200, 302)` گاهی مشروع است (ری‌دایرکت پس از POST)، اما وقتی برای یک
`GET` استفاده شود یعنی «نمی‌دانم چه باید بشود». `(200,302,404)` هرگز مشروع
نیست: ۴۰۴ یعنی روت وجود ندارد و تست باید همان را فریاد بزند.

## ۴) پاسخ به سؤال شما: چه کار کنیم؟

نظر صریح من: **تست جدید ننویسیم تا دو شکاف بالا بسته شود.** افزودن تست روی
هارنسی که شکست را می‌بلعد، فقط اعتماد کاذب تولید می‌کند.

### فاز ۱ — بازگرداندن صداقت (پیش‌نیاز مطلق)
۱. **۲۷ فایل مرورگری fail-safe شوند**: یک ماژول مشترک
   `tests/support/browser-harness.js` با `check(name, cond)`، شمارندهٔ
   pass/fail، و `process.exit(failures ? 1 : 0)`؛ `catch` باید شکست را
   **ثبت** کند نه ببلعد. الگو از همان ۷ فایل سالم گرفته شود.
۲. **`run_all.py` سخت‌گیر شود**: علاوه بر `returncode`، وجود `✗` یا
   `JS_ERROR` در خروجی هم شکست تلقی شود (دفاع لایه‌دوم).
۳. **آن ۱ مورد `(200,302,404)`** به انتظار قطعی تبدیل شود.

*معیار پذیرش فاز ۱:* با خاموش‌کردن عمدی سرور، **هر ۳۴** فایل باید کد خروج
غیرصفر بدهند. امروز فقط ۷ تا می‌دهند. این تست‌ِ تست است.

### فاز ۲ — پوشش روت‌های پارامتردار (بیشترین سود)
۱. **آزمون فراگیر روت** (route-sweep) از روی `routes/*.php`: هر روت با
   کاربر واقعیِ نقش‌دار زده شود و ادعا شود **هرگز ۵۰۰ نمی‌دهد** و برای
   کاربر بی‌مجوز ۴۰۳/۴۰۲ می‌دهد. این یک تست است ولی ۷۳۵ روت را پوشش می‌دهد
   و رگرسیون‌های فاجعه‌بار را می‌گیرد.
۲. **فیکسچرهای دادهٔ واقعی**: برای رسیدن به `{id}` باید بنر/آگهی/تیکت واقعی
   ساخته شود. یک `TestDataFactory` (بر پایهٔ همان الگوی `$marker` و پاک‌سازی
   در `tearDown` که در `OutboxQueueDlqRuntimeTest` هست) لازم است.
۳. اولویت با پول: `wallet` (۱۴)، سپس `admin` تغییر وضعیت (approve/reject).

### فاز ۳ — عمق منطقی (اکشن‌محور واقعی)
برای هر مسیر پولی، الگوی چهارگانه:
**حالت اولیه (DB) → اکشن HTTP → حالت نهایی (DB) → اثر جانبی
(outbox/لاگ/نوتیف)**. این همان کاری است که `scenario_wallet.py` با
`db_scalar` درست انجام می‌دهد و باید به بقیه تعمیم یابد.
شروع از ۶ کنترلر بی‌ارجاع، با `TransferController` در صدر.

### فاز ۴ — دروازهٔ کیفیت
یک تست معماری که **خودش جلوی برگشت را بگیرد**:
- هیچ `browser_*.js` بدون `process.exit(1)` نباشد
- هیچ ادعای `(200, 302, 404)` اضافه نشود
پروژه از قبل `phpunit.architecture.xml` با ۸۱۶ تست دارد؛ جای طبیعی همین‌جاست.

## ۶) هشدار صادقانه دربارهٔ گزارش قبلی خودم

این را باید همان موقع می‌سنجیدم. «۳۴/۳۴ سبز» تا قبل از فاز ۱ نباید به‌عنوان
